# Cloud Collab

Cloud Collab is a static, single-page collaborative workspace app. The browser UI is vanilla ES-module JavaScript; Supabase provides Auth, PostgreSQL, RLS, and secure database functions. It is designed to deploy directly to GitHub Pages without a server runtime.

## Current feature set

- Email/password sign-up, sign-in, session persistence, password reset, and sign-out.
- Multiple isolated workspaces with owner/admin/editor/viewer roles.
- Workspace creation, switching, settings, member list, role management, and owner-only deletion policy.
- Secure, hashed, seven-day invitation links with email matching and accept flow.
- Nested Markdown pages with page icons, CRUD, safe rendering, search, timestamps, and optimistic-concurrency save protection.
- Responsive sidebar, mobile navigation, profile editing, and appearance preference.
- Versioned SQL migration, RLS policies, and GitHub Pages Actions deployment.

## Configure Supabase

1. Create a Supabase project and run `supabase/migrations/202610230001_initial.sql` in the SQL Editor (or apply it through the Supabase CLI). See `SUPABASE.json` for the configuration checklist.
2. In `assets/js/config.js`, replace `YOUR-PROJECT` and `YOUR-PUBLISHABLE-ANON-KEY` with the project URL and publishable/anon key. These two browser values are expected to be public. Never add a service-role key.
3. In Supabase Auth → URL Configuration, add both the local URL and the deployed GitHub Pages URL to Site URL / Redirect URLs. For a project site, use `https://USER.github.io/REPOSITORY/`.
4. Configure email confirmation and SMTP in Supabase if you want production email delivery. Invitation links are generated by the app and can be copied into any channel; an email provider integration can be added later without exposing credentials.

## Run locally

Because ES modules and Supabase redirects need an HTTP origin, serve the repository with any static server, for example `python -m http.server 8080`, then open `http://localhost:8080`. There is no build step and no dependency install.

## Deploy

Push the repository to GitHub, enable Pages with **GitHub Actions**, and let `.github/workflows/deploy-pages.yml` publish the repository. GitHub Pages serves the relative asset paths correctly for both root and repository sites. `404.html` provides a simple fallback redirect.

## Security notes and verification

All private tables have RLS enabled. Workspace membership, role checks, page writes, invitation creation, and invitation acceptance are enforced by PostgreSQL policies/functions; client-side checks are only for user experience. The invitation token is high entropy and only its SHA-256 hash is stored. The generated raw token is returned once so it can be shared.

Recommended checks after applying the migration:

- Sign up two users, create a workspace with user one, and invite user two.
- Accept the link while signed in as the invited email; verify the membership appears after refresh.
- Verify viewer page writes fail, editor page writes succeed, and an editor cannot change roles.
- Try querying another workspace's pages and members from the Supabase client; RLS should return no rows or an error.
- Verify expired/revoked tokens cannot be accepted and that a token for another email is rejected.

## Known limitations

The first release intentionally keeps collaboration reliable and small: invitation delivery is copy-link based, page reordering and invitation revocation UI are not yet exposed, and live presence/realtime cursors are not included. The database schema is ready for those additions, and stale page saves are rejected rather than silently overwritten.
